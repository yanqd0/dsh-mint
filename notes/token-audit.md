# 会话 token / 成本审计（token-audit）

> 口径：本文件是**会话级** token 与成本的**审计方法 + 一次完整基线**。每请求固定注入的预算复盘见
> [session-cost-review.md](session-cost-review.md)（那份回答「插件注入值不值」，本份回答「这次会话花在哪、
> 能不能省、子代理之间重复了多少」）。
>
> 样本：2026-10-08 一个 dsh-mint 会话及其 **3 个子代理**（worktree 并行批次：两个实现节点 + 一个调研节点），
> 共 **273 次 LLM 请求**（main 107 + 子代理 166）。
> 数据全部来自本机落盘文件；§2 给出字段路径与可复现脚本要点，换会话只需换路径。

## 1. 结论摘要

| 结论 | 数值 |
| --- | --- |
| 总 token（main + 3 子代理） | **38,833,723**（273 步） |
| 成本（账本口径，可归属部分） | **≈¥2.06**；同窗口账本合计 ¥3.3163（含 1 条无法归属的 turn ¥1.3756） |
| 提示结构 | 未缓存输入 388,429（1.0%）· 缓存读 38,217,728（**98.4%**）· 输出 227,566 |
| 成本构成 | 输出 **44%** · 缓存读 37% · 未缓存输入 19% |
| 反解单价 | 未缓存输入 **¥1.00/1M** · 缓存命中 **¥0.02/1M** · 输出 **¥4.00/1M** |
| 上下文轨迹（首步 → 末步） | main 13,571 → **294,451**；子代理 Q 18,072 → 204,984；P 16,680 → 62,807；R 14,011 → 57,013 |
| 最大单点 | 子代理 Q：98 步 / 15,494,936 tokens / ≈¥0.735（全会话 **36%**） |
| 跨会话重复读 | 209,752 B（≈50k tokens） |
| 前缀缓存 | 四个会话 step-1 的 `cacheReadTokens` 都恰好 **8,320**；两个 brief 的最长公共前缀仅 **57 字符** |

三条读法：

1. **token 数被缓存读支配（98%），钱被输出支配（44%）**——只盯 token 数会优化错目标。
2. **真正的驱动量是「上下文长度 × 步数」**：main 平均每步 188k tokens，107 步就是 20.1M。
3. 缓存把「重复」压得很便宜（¥0.02/1M，是未缓存输入的 1/50），但**重复本身没有消失**：一旦漏出缓存
   （新内容、前缀分叉），就按 ¥1/1M 计费。

## 2. 数据源与可复现方法

三个来源 + 一份文件体量：

| 来源 | 路径 | 提供什么 |
| --- | --- | --- |
| 会话 transcript | `~/.dsh/sessions/<workspace>/<session-dir>/session.v4.jsonl.zstd` | 逐 step 用量；每一次工具调用与结果（＝上下文构成的原始数据） |
| 用量账本 | `~/.dsh/.dshw-usage.json` | 每个 turn 的 `cost` 与 `tokens`（钱的唯一来源） |
| 会话投影缓存 | `~/.dsh/storages/session_projcache/sessions/<id>.json` | 会话/子代理的实时投影（plan DAG 的 `samples[].tokens` 由它读出） |
| 文件体量 | `git ls-files` + 文件大小/行扫描 | 大文件清单与注释占比 |

字段路径（v4 形状，本次实测）：

- 解压：`zstdcat <file> > /tmp/sess.jsonl`（每行一个事件，用 `type` 区分）。
- 逐 step 用量在 **`assistant/message` 的 `data.usage`**，字段：`inputTokens`（未缓存输入）、
  `cacheReadTokens`（缓存命中）、`cacheWriteTokens`、`outputTokens`、`totalTokens`
  （= 前四者之和，本次 107 步全部成立）。
- 工具配对：调用在 `tool/call` 的 `data.callId` / `data.name` / `data.arguments`；结果在 `tool/result` 的
  **`data.message.toolCallId`**（不是 `data.toolCallId`）；文本在 `data.message.content[].text`。
- 文件读取归因：`read` 的 `arguments.file_path` + 上面的结果文本字节数。
- 账本事件：`events[]` 每项 `{ts, day, model, cost, tokens}`；**没有会话/项目标识**（见 §7）。

脚本要点（约 40 行即可复现本文表格）：

```python
import json, collections

usage = collections.Counter()
calls = {}
for line in open('/tmp/sess.jsonl'):
    ev = json.loads(line)
    d = ev.get('data') or {}
    if ev.get('type') == 'tool/call':
        calls[d.get('callId')] = d
    elif ev.get('type') == 'assistant/message':
        u = d.get('usage') or {}
        for k in ('inputTokens', 'cacheReadTokens', 'cacheWriteTokens',
                  'outputTokens', 'totalTokens'):
            usage[k] += u.get(k, 0) or 0
    elif ev.get('type') == 'tool/result':
        msg = d.get('message') or {}
        call = calls.get(msg.get('toolCallId') or d.get('toolCallId')) or {}
        size = sum(len(b.get('text', ''))
                   for b in (msg.get('content') or []) if b.get('type') == 'text')
        # 这里按 (会话, 工具, 文件路径) 归集 size，即可得到 §5.1 / §5.2 的表
print(usage)
```

换算：**字节 → token 用本次实测比值**（main 4.21 B/token，子代理 3.37–4.84），不要用固定 4。

## 4. 成本口径：单价反解

账本只给每个 turn 的 `cost` 与 `tokens` 合计，没有拆分；模型单价本机无处可读。做法：取能与四个会话逐条
对上的 7 个 turn，用其 (未缓存输入, 缓存读, 输出) 三元组与账本 `cost` 做最小二乘，解出整数级吻合的单价：

| 分量 | 单价 | 本次占比（金额） |
| --- | --- | --- |
| 未缓存输入 | ¥1.00 / 1M | 19%（¥0.388） |
| 缓存命中 | ¥0.02 / 1M（未缓存输入的 **2%**） | 37%（¥0.764） |
| 输出 | ¥4.00 / 1M | **44%**（¥0.910） |

**这条换算是本文最有用的工具**：没有它，38.8M tokens 无法回答「贵在哪」。反解残差近 0，说明这三个数就是
真单价；也正说明本机没有任何地方写着它们（手册缺口）。换模型/换价时必须重新反解，不要硬编码。

账本窗口：8 条 turn 事件、合计 `66,861,354` tokens / `¥3.3163`。其中 **7 条与本文的四个会话逐条精确对上**，
剩下 1 条（`31,794,911` tokens / `¥1.3756`）对不上任何会话——账本无归属字段，无法判断它属于谁（§7 第 1 条）。
当天 `todayUsage` ¥3.68、余额 ¥11.31。

## 6. 子代理与前缀缓存（实测）

- **系统前缀是跨会话共享的**：四个会话 step-1 的 `cacheReadTokens` 都**恰好等于 8,320**（main 8,832）——
  system prompt + 工具目录 + AGENTS 注入这一段已在缓存里命中。
- **brief 部分完全没吃到缓存**：两个实现子代理的 brief 最长公共前缀只有 **57 字符 / 101 B**
  （首行「…负责节点 ehub」与「…负责节点 e199」就分叉），逐行完全相同的只有 32 行 / 1,081 B
  （占其中一个 brief 的 9%）。两个子代理 step-1 的 `cacheReadTokens` 相同、`inputTokens` 分别
  8,360 / 9,752 → **缓存停在系统前缀，brief 全部按未缓存输入计费**。
- brief 体量：P 11,857 B、Q 16,655 B、R 2,726 B（合计 ≈31 KB ≈ 13k 输出 token，输出单价 ¥4/1M）。
- **已发生的浪费**：harness 会按工作目录注入 `AGENTS.md`，而 brief 又要求「开工必读」三份 AGENTS →
  每个子代理多读 ≈18.8 KB，两个合计 ≈37.6 KB。
- 收益上限估算：把逐字节相同的「纪律头」（≈2–4 KB）前置，第二个子代理可缓存读它，省的是未缓存输入与
  main 的输出，量级 **¥0.001–0.01/次**——比「拆节点」小两个数量级（Q 一个节点就 ¥0.735）。

## 7. 已知口径缺口与坑

1. **账本不归集**：`events[]` 只有 `{ts, day, model, cost, tokens}`，没有会话/项目/cwd → 多项目并行时无法
   归集；且与逐 step 求和口径不一致（本窗口账本 66.9M vs 本文四会话 38.8M，差额含那条 31.8M 的不可归属事件）。
2. **会话存储命名/枚举不一致**：主会话目录 `session-<uuid>`，子代理 `<uuid>`，与主会话平铺、无父子索引 →
   会话树只能靠猜（本次靠 grep 会话 id 才定位）。
3. **单价不在本地**：只能反解（§4）。
4. **存储格式未公开**：`session.v4.jsonl.zstd` 的字段位置（`data.usage`、`data.message.toolCallId`）是实测
   反推；换宿主版本可能漂。
5. **前缀缓存无手册**：作用域、失效条件、可测性都靠实测（§6）。
6. **DAG 看不到 main**：节点的 `tokens` 只在子代理收尾时由宿主实测写入，main 自己的节点没有（读了会是整条
   主会话累计，语义不对）；plan 收口也不记录「这个 plan 花了多少」。
7. **本仓口径缺口**：worktree 会话前缀把 `session-…` 一律截成 `session-`（跨会话路径与分支同名，开工点
   `prune` 删掉的上一批树与本批同目录）；节点粒度只有「能否并行」没有「贵不贵」；brief 模板没有「前缀一致」
   要求；读取粒度没有范围读口径。

## 8. 两条评估结论

### 8.1 「文件小、职责单一、大幅减少注释 → 有利 LLM」

- **文件小 + 职责单一：成立**，但要与「范围读」配合——单次整读的直接金额 <1%，它真正的代价是把上下文推高。
- **大幅减少注释：赔率很差**。按 §4 单价，本次读入的 `src/**` 字节里注释约 41k tokens；即使全删，省
  ≈¥0.08（占该会话 ≈¥2.06 的 4%）；而一次返工实测 ¥0.1–0.7（子代理重跑一轮）。该减的是**复述类型/签名/
  实现细节**的注释，不是「为什么/不变量/契约」——本次多处靠 why 注释避免踩坑：`dag-worktree.ts` 的
  「静默回落到主工作树就等于丢掉隔离」直接决定了新增守卫的写法；`dag.ts` 的「无 `node:` import，因为浏览器
  包会内联它」被写进 brief 并用守卫钉住。
- **「不利于人类维护」这个代价不必付**：拆小文件、删 what 注释对人类同样友好；长解释应搬进 `notes/` 与
  AGENTS 口径（单一真源），而不是删除。
- 这句话忽略的两项更大开销：**测试文件**（本次 `tests/**` 读入 232.9KB）与**跨会话重复读**（210KB）。

### 8.2 token 统计能否做成公共能力

**可以，且边界清楚**：数据源全在本地（§2 三处），公共底座是「读会话存储 + 账本 + 投影并归并」，形态可以是
宿主插件（工具/面板）或离线模块 / CLI。**但底座优先**：账本缺会话维度、单价不在本地、会话树无枚举口径
（§7 的 1–3）不解决，展示面只会把猜出来的数画得更好看。风险：未公开的存储格式（必须版本适配或 fail-loud）、
读取全量会话内容的隐私面（只读 + 只聚合 + 不落副本）、单价与缓存规则会变（报告要能自证，例如显示反解出的
单价与残差）。
