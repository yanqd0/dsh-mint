# 跨项目登记（cross-project）

> 触发：发现的问题**属于别的项目的能力面**，在本项目改不了，但想登记到对方台账。
> 命令面与门禁见 `commands.md` / `host-dsh.md`；label 命名见 `labels.md`。

## 何时跨项目（可判定）

判据只有一条：**「改哪一个仓库/项目才能修掉它？」**

| 场景 | 归属 | 例（本仓真实案例） |
|---|---|---|
| 缺陷/缺口在**对方的实现或手册**里，本项目只是受害者 | **跨项目** | dsh 手册缺 seat 索引、`webServer` prefix 规则、Inspect 全量查询太贵 |
| 缺陷在**本项目自己的代码/流程**里 | 本项目 | 本插件的门禁写错、skill 口径过时 |
| 本项目**用法**上踩坑，但根因是上游语义 | 先在**本项目**记（并把结论写进 `notes/`）；只有当对方需要改才跨项目 | 上游设计张力（如 approval scope）尚未定案 |

- 反例（**不要**跨项目）：把本仓的 TODO、未完成实现、内部重构登记到别人家。
- 正例：写 `notes/` 时反复「只能读上游源码/产物才知道」——那就是对方的缺口。
- 判不准时**先问用户**；不要两边都提一遍。

## 目标项目确认（先做，再写）

- 先 `mint({ args: ["project","list"] })` 列本机已有项目。注意 `project list`（含 `--json`）**只有项目名**，
  没有描述/路径，不能据此判断某个项目负责什么。
- 目标名**不在清单** → 不登记：反问用户（换目标 or 确需新建项目库）。工具本身也会拒绝，
  但仍**不要**用 `-p <猜测名>` 去试——白跑一次，且没有任何信息量。
- 清单里存在**命名相近**的多个项目（如 `dsh-mint` / `dsh-covtrim` / `dsh-dev-dsh`、`mint` / `dsh-mint`），
  或凭现有信息判不准归属 → **询问用户**：给候选 + 各自一句判据，让用户选，不要猜。
- 目标明确且存在 → 继续。跨项目**读**会顺带把当前目录写进对方的 `abs_dir` 列表，所以也别拿 `-p` 做无意义探测。

## kind 判定（几乎只有两种）

| 场景 | kind |
|---|---|
| 对方的实现/手册有缺陷，我们被它坑到 | `problem` |
| 对方缺一个能力/口径/契约，而我们在依赖它 | `requirement` |

- **不要用 `task`**：task 是对方自己的杂务，外部登记不该替对方排杂务。
- problem / requirement 分不清 → **询问用户**，不猜。
- priority 按我们被影响的程度给（影响面 + 是否有本地绕行）；不确定就 P2。

## 命令形态（`-p` 必须在子命令之前）

```js
mint({ args: ['-p', 'dsh-dev-dsh', 'list', '--status', 'open'] }); // 读：直接放行
mint({
  args: [
    '-p',
    'dsh-dev-dsh',
    'issue',
    'add',
    '<标题>',
    '--kind',
    'requirement',
    '--priority',
    '1',
    '--label',
    'docs,<来源项目>',
  ],
}); // 写：首次弹确认
mint({
  args: ['-p', 'dsh-dev-dsh', 'plan', 'create', '<标题>', '--milestone', '<对方 running id>'],
});
```

- `--project` 只接受**项目名**（mint 数据目录 `projects/` 下的目录名），不是路径；名字里不能有 `/` `\`。
  候选用 `mint({ args: ["project","list"] })` 查。
- 目标项目不存在 → 工具直接拒绝并给候选（**不会**静默新建项目库，也不会落到本项目）。
- `MINT_DB_PATH` 单文件模式下不支持跨项目。

## 来源标注（必须留，但不必进标题）

在**对方**项目登记时，必须留下来源，否则对方无法回溯是谁提的：

1. **label 追加来源项目名**（强制）：小写、等于 mint 项目名（如 `dsh-mint`），与内容 label 并列
   （例：`docs,dogfood,dsh-mint`）。label 自动注册；来源 label 不替代内容 label，也不占「≤5 个」之外的额外含义。
2. **body 首节 `## 来源`**（通常必需）：首行写 `来源：<来源项目> <plan/issue 指针> + 一句话场景`，
   紧跟实测证据（版本、命令、输出要点）。对理解和解决该 issue 通常很有帮助。
   指针给**本仓**的 plan/issue 编号或 `notes/` 文件，便于对方回查。
3. **标题可选、不重复来源**：来源已由 label + body 表达，标题只写对方能独立看懂的现象/需求即可——
   省下的长度留给内容。跨项目不适用「标题自解释就不写 body」：来源与证据必须留。
4. **不重复提**：对方已有 issue 覆盖的内容，只补「我们的实测证据/差异」，不另起一条（先搜：
   `mint({ args: ["-p","<对方>","search","<关键词>"] })`）。

## 内容纪律（报问题，不越权给方案）

- **可以给**：现象与复现步骤、实测证据、影响面、需求描述、建议。
- **不要给具体实现方案**：怎么改由目标项目自己定——外部方案未必专业，还可能把对方的设计绑死。
- 确有把握时才附方案，且写成「建议（可选）：…」并说明理由与代价；不要写成必须照做。

## 反查方向（两边都不认账的解药）

`mint` 的 link 是**库内**语义（issue id 跨项目会撞），跨项目只能用文本 cross-ref：

- **对方侧**（被登记的项目）：`## 来源` 首节 → 指回来源项目。
- **来源侧**（本项目）：在**本次工作**的 plan/issue body 里记一行「已向 `<对方项目>` #N 登记」，
  必要时把对方的验收条件抄一句。用 `issue set <id> --body-append`（见 `body-editing.md`）。
- 登记完**不要**把对方 issue 挂进本项目的 plan/milestone（跨库 id 无意义）。

## 门禁与通道

- **写操作**：同一会话 + 同一目标项目，首次弹一次确认（文案含目标项目与动作），之后免问；
  换目标项目或换会话会再问。这是宿主 `tools/pre-execute` 的门禁，**不是**沙箱提权。
- **读/写判据**：以子命令白名单判（`list/show/search/help` + 容器与 label/project 的读叶子）。
  `-p` 之后**只有根标志**（`-V`/`--version`/`--help*`）或干脆没有子命令 ⇒ 读（后者是 usage error、
  不写库）。**子命令之后的 `--help` 不算读**：它可能是 `--` 后的取值（`issue add -- --help` 会真的
  建一条标题为 `--help` 的 issue），所以照写确认（#98/#99）。想查参数就在**本项目**里查。
- **探测去重**：同一（入口, 项目目录）的 `project list --json` 短时间内只跑一次（5s 记忆），
  门禁与工具侧共用同一次 spawn；`project create/set` 成功后立即失效（#106）。
- **子代理**：approval 被 pin `never` ⇒ `ask` 退化为拒绝。跨项目**读**可用，**写**不可用
  （子代理只做调研，登记交回主 agent）。
- **bash 兜底**：只在工具不可用/插件未安装时才用。插件在场时，可识别的裸
  `mint -p <项目> <写命令>`（含 `MINT_PROJECT=` 前缀）走同一道确认；引号、重定向、`$( )`、
  脚本文件等形态不识别，那时只有沙箱提权审批兜底。
- **不做**：`--db`（单文件模式）、跨项目聚合视图。两者都不在本 skill 的支持面内。
