# 执行阶段全景 DAG 与分派（dag-exec）

> 触发：**方案定稿后**（宿主 plan 正文已定），把方案落成可执行的 DAG 并分层派活。
> 调研阶段（未定稿）见 `plan-dag.md`；批次判据与派发/等待纪律见 `parallel-exec.md`。

与调研阶段不同：执行阶段的 DAG **全景已知且确定**——节点是 issue/子任务，边是依赖，不用边跑边猜。

## 1. 定稿后第一步：产出全景 DAG

- 节点 = 本 plan 的 issue（或 issue 内的子任务）；边 = 「谁必须先完成」。
- 落点：写进 **plan body**（`## 并行批次` 段）。**没有 DAG 工具时就以「依赖批次表」等价表达，
  沿用既有 `## 并行批次` 段格式，不另立新格式。**
- 产出即可核对：每个节点都有明确归属（哪个 issue/哪个 agent），每条边都有理由（文件冲突、接口依赖、写序）。

## 2. 分层：DAG 的「层」= 批次

复用 `parallel-exec.md` §1 的**五轴**判据（文件 / 共享生成物 / 命令 / git 与 mint 写 / 语义依赖），
把无依赖的节点放进同一层；**同层 = 同一批**，在**同一条 assistant message** 里批量派发（并行启动，不要逐个等）。

- 一 issue 一子代理；3–6 路为宜。
- 同一 issue 不拆给多人；子代理不得再派子代理。
- 层与层之间是依赖，不是等待点：派完上一层就去做与下一层无冲突的独立工作。

## 3. 分派边界：什么给子代理、什么留 main

| 任务性质 | 给谁 | 理由 |
|---|---|---|
| 测试、验证、复核（跑命令、看输出、比对期望） | **子代理** | context 需求小、结果可客观判定，判定者不必是写码者 |
| 远程调用、命令调用、工具调用（查接口、拉数据、批量执行） | **子代理** | 中间产物留在子代理会话里，main 只收结论 |
| 单文件小改、格式/文档类改动 | **子代理** | 白名单可精确圈定 |
| 总体评估、方案取舍、跨项一致性判断 | **main** | 要串起全局 context，子代理看不到父对话 |
| 用户决策与对外沟通（`ask_user_question`） | **main** | 子代理不能提问（`DELEGATED_CALLER`） |
| 开发流程控制（状态机推进、批次调度、收口） | **main** | 单写者职责 |
| **对 context 依赖大的复杂任务**（多文件反复推理、需历史结论） | **main** | 抽不出必要注入，派了它也要重走一遍 |
| 「为派活准备注入内容本身就过大」 | **main** | 明确允许不强求（见 `plan-dag.md` §1） |

**反例（把高 context 任务误派子代理的代价）**：让子代理去改一个「必须同时理解宿主事件签名、本仓守卫、
上一条 issue 的既有结论」的模块——它看不到父对话，只能重新调研，既慢又容易与既有口径冲突；
这类任务正确做法是 main 亲跑，只把**可独立验收的测试/验证**派出去。

## 4. 单写者不变

- **git 提交与一切 mint 写（`state`/`plan`/`issue`）归 main，逐 issue 串行**（避免 git index 竞态与互相夹带）。
- `build` / `test:coverage` / 格式化 / 装依赖等重命令与串行独占生成物（`dist/`、`coverage/`、lockfile、`CHANGELOG.md`）归 main。
- 子代理只改**自己白名单内的文件**，自检只用只读命令。
- 完整定义见 `parallel-exec.md` §4，本文件不重复。

## 5. 返工不改环

- DAG **无环**是硬约束。
- 测试失败 / 调研否定 → **在尾部追加节点**（`retest`、新调研节点、修复节点），而**不是**回连旧节点造环。
- 追加时同步状态机：`issue state retest <id> --test-cmd "<精确手法>"` 打回，修完再 `state commit`（新 sha）→ 统一测试。
- 「已完成的节点」保留其终态判定（`pass`/`fail`），返工体现为**新增的**节点与边。
