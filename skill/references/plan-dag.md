# 调研阶段 DAG 化（plan-dag）

> 触发：**方案未定稿前**的调研（摸清现状、比对方案、核查外部事实），需要并行提速、或需要省 main agent 的 context。
> 与执行阶段的分工见 `dag-exec.md`；派发/等待纪律见 `parallel-exec.md`。

调研阶段的 DAG **不是预先给定的**：全景不可预览，只能一轮一轮长出来。所以按「**总—分—总**」为一个阶段递进，
若干轮后信息完备才写方案。

## 1. 何时派子代理 / 何时 main 亲跑

| | 判据 |
|---|---|
| **派子代理** | 可并行（分支互不依赖）；单体 context 需求小（一份文件、一个目录、一个命令、一次检索）；结果可客观判定（正文/输出/退出码能自证） |
| **main 亲跑** | 用户决策；跨项总体评估与取舍；开发流程控制；**对 context 依赖大的复杂任务**（要串起父对话历史、要反复跨文件推理）；**为派活而准备的注入内容本身就过大** |

- 第二列最后一条是**允许不强求**的边界：若「把必要 context 抽出来前置注入」比 main 自己干还贵，就别派。
- 派子代理的收益有两种，按场景取：**并行**（多路同时推进）与**省 context**（把大段中间产物留在子代理会话里，
  只让它回结论）。当两者冲突时，优先保「结论可核对」。
- 子代理**不能再派子代理**（委派深度默认 1）。

## 2. 一个阶段 = 总—分—总

    ┌ 总① ────────────────────────────────────────┐
    │ main：拆本轮 DAG（要答哪几个问题）           │
    │       只问「不答就无法继续」的用户决策        │
    └───────────────┬─────────────────────────────┘
                    ▼ 分（并行）
        子代理 A / 子代理 B / …（一节点一子代理）
                    ▼
    ┌ 总② ────────────────────────────────────────┐
    │ main：合并结论、更新 DAG、判断是否需要用户决策 │
    └───────────────┬─────────────────────────────┘
        需要决策 → 一次 ask_user_question → 进下一阶段
        不需要   → 直接进下一阶段

- **「总」是唯一允许向用户提问的位置**。子代理**不得**自行 `ask_user_question`（宿主会以 `DELEGATED_CALLER`
  拒绝根 agent 之外的调用）；遇决策把它写进最终回复（问题 + 选项 + 建议 + 影响），由根 agent 合并成一次提问。
- 一次「总」里**尽量只问一次**：把同一轮攒下的决策合并成一次 `ask_user_question`，别逐条问。
- 阶段可以连续多个：`总①→分→总②→总①'→分'→总②'→…`。每轮都要**缩减不确定性**，否则说明该问题该由 main 直接读完。

## 3. 注入前置纪律（派活提示词五段）

子代理看不到父对话与工具输出，必要的 context 必须在**开头**给全：

1. **目标**：要产出什么、写到哪（含 issue 号）；
2. **文件或范围白名单**：逐一点名；
3. **验收**：怎么算完成（只读自检命令、期望输出）；
4. **既有结论与已排除方案**：父对话里查到的、试过不行的——不写就等于让它重走一遍；
5. **禁令**：不 git、不 mint 写、不跑重命令、不动他人文件、遇用户决策写进最终回复。

- **指针优于复述**：issue body 用只读 `mint({args:["issue","get","<id>","body"]})` 取，不要贴父对话、不要复述 AGENTS.md。
- **过长就转 main**：为凑齐第 4 段而要摘抄大量上下文时，直接由 main 亲跑。

## 4. 调研阶段怎么留痕

- 每一轮「总」都记一条 DAG 节点：`id`、**≤6 字短标签**（面板显示用）、完整标题（悬停显示）、本轮判定结果。
- 节点状态：`pending`（未跑）/ `running` / `done`，终态带 `verdict`（`pass` = 有结论可采信，`fail` = 方向被否定/结论不可用）。
- 语义映射：**「分」= 并行节点**（彼此无依赖）；**「总」= 汇合节点**（依赖上一轮的「分」节点）。
- 记录的机器载体是 `mint_plan_dag` 工具（`init`/`add`/`set`/`get`；实现见 plan #31）。
  工具未就绪时，手写 DAG 或写进 plan body 同样成立——**先有结构，后有载体**。
- 状态更新尽量由**刚跑完的那个子代理/主 agent 自己写**；若 main 写更省 token（结论已在 main 手里），就 main 写。

## 5. 分界节点

- **宿主 plan 正文定稿 = 分界**：此前 DAG 动态生长（本文件），此后为静态全景（`dag-exec.md`）。
- 分界只标注「到此调研结束」，不要求调研节点全部 `pass`：被否定的方向（`fail`）同样是有效结论，照常入图。

## 6. 纪律（与执行阶段共用）

- 不 `sleep`、不轮询 `list_agents`：派发后继续做独立工作，结算通知会自动到。
- 真被阻塞才 `job_output(<id>, wait: true)`，且只用于一次性后台 job，不用于子代理（见 `parallel-exec.md` §5）。
- 收串行/独占：git 与一切 mint 写、重命令（build / test:coverage / 装依赖）一律归 main。
