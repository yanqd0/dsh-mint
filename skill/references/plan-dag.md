# 调研阶段 DAG 化（plan-dag）

> 触发：**进计划模式即启动**——方案未定稿前的调研（摸清现状、比对方案、核查外部事实）一律先画 DAG，
> **无并行分支、main 全程亲跑同样要画**（不做「要不要画」的取舍）。
> 第一步固定：`mint_plan_dag({action:"init",title:"<本计划>"})` 给「总①」落一个节点，
> 之后才决定是否派子代理（判据见 §1）。
> 与执行阶段的分工见 `dag-exec.md`；派发/等待纪律见 `parallel-exec.md`。

调研阶段的 DAG **不是预先给定的**：全景不可预览，只能一轮一轮长出来。所以按「**总—分—总**」为一个阶段递进，
若干轮后信息完备才写方案。

## 1. 何时派子代理 / 何时 main 亲跑

| | 判据 |
|---|---|
| **派子代理** | 可并行（分支互不依赖）；单体 context 需求小（一份文件、一个目录、一个命令、一次检索）；结果可客观判定（正文/输出/退出码能自证） |
| **main 亲跑** | 用户决策；跨项总体评估与取舍；开发流程控制；**对 context 依赖大的复杂任务**（要串起父对话历史、要反复跨文件推理）；**为派活而准备的注入内容本身就过大** |

- 第二列最后一条是**允许不强求**的边界：若「把必要 context 抽出来前置注入」比 main 自己干还贵，就别派。
- 派子代理的收益有两种，按场景取：**并行**（多路同时推进）与**省 context**（把大段中间产物留在子代理会话里，
  只让它回结论）。当两者冲突时，优先保「结论可核对」。
- 子代理**不能再派子代理**（委派深度默认 1）。

## 2. 一个阶段 = 总—分—总

    ┌ 总① ────────────────────────────────────────┐
    │ main：拆本轮 DAG（要答哪几个问题）           │
    │       只问「不答就无法继续」的用户决策        │
    └───────────────┬─────────────────────────────┘
                    ▼ 分（并行）
        子代理 A / 子代理 B / …（一节点一子代理）
                    ▼
    ┌ 总② ────────────────────────────────────────┐
    │ main：合并结论、更新 DAG、判断是否需要用户决策 │
    └───────────────┬─────────────────────────────┘
        需要决策 → 一次 ask_user_question → 进下一阶段
        不需要   → 直接进下一阶段

- **「总」是唯一允许向用户提问的位置**。子代理**不得**自行 `ask_user_question`（宿主会以 `DELEGATED_CALLER`
  拒绝根 agent 之外的调用）；遇决策把它写进最终回复（问题 + 选项 + 建议 + 影响），由根 agent 合并成一次提问。
- 一次「总」里**尽量只问一次**：把同一轮攒下的决策合并成一次 `ask_user_question`，别逐条问。
- 阶段可以连续多个：`总①→分→总②→总①'→分'→总②'→…`。每轮都要**缩减不确定性**，否则说明该问题该由 main 直接读完。

## 3. 注入前置纪律（派活提示词五段）

子代理看不到父对话与工具输出，必要的 context 必须在**开头**给全：

1. **目标**：要产出什么、写到哪（含 issue 号）；
2. **文件或范围白名单**：逐一点名；
3. **验收**：怎么算完成（只读自检命令、期望输出）；
4. **既有结论与已排除方案**：父对话里查到的、试过不行的——不写就等于让它重走一遍；
5. **禁令**：不 git、不 mint 写、不跑重命令、不动他人文件、遇用户决策写进最终回复。

- **指针优于复述**：issue body 用只读 `mint({args:["issue","get","<id>","body"]})` 取，不要贴父对话、不要复述 AGENTS.md。
- **过长就转 main**：为凑齐第 4 段而要摘抄大量上下文时，直接由 main 亲跑。

## 3.1 空 DAG（0 节点）面板不会打开

- **空图 = 面板与图都不存在**：plan-dag 面板自动打开的判据是「**本会话 DAG ≥1 节点**且该 kind 的 tab 未开」，
  0 节点的文档不满足，于是既看不到面板、也看不到图。
- 所以「不 `init`」与「`init` 了不落节点」等价：这次调研在面板上**没有任何留痕**，
  下一轮（或换会话）无从复核当时查了什么、得出了什么。
- 首轮的第一件事就是把「总①」`add` 进去（哪怕只有一个节点），面板才会出现。
- **别指望再提醒一次**：空图软提醒（#169/#171）把「没有 DAG」与「有 DAG 但 0 节点」当**两个**状态，
  各提醒一次，同一状态不重复。所以在收到第二次提醒（`init` 之后那句）时，唯一还没做的就是把节点 `add` 进去——
  「`init` 完先 `add` 一个节点」是同一个收尾动作，不是两步。

## 4. 调研阶段怎么留痕

- **每轮开始就 `add` 节点并 `set running`**（不要等这轮跑完再补记）：`id`、**≤6 字短标签**（面板显示用）、
  完整标题（悬停显示）；本轮结束再 `set done` 带 `verdict`。
- **不落节点 = 这次调研在面板上不存在**（见 §3.1）；节点不是给面板看的装饰，它就是本轮要答的那个问题本身。
- 节点状态：`pending`（未跑）/ `running` / `done`，终态带 `verdict`（`pass` = 有结论可采信，`fail` = 方向被否定/结论不可用）。
- 语义映射：**「分」= 并行节点**（彼此无依赖）；**「总」= 汇合节点**（依赖上一轮的「分」节点）。
- 记录的机器载体是 `mint_plan_dag` 工具（`init`/`add`/`set`/`get`；实现见 plan #31）。
  工具未就绪时，手写 DAG 或写进 plan body 同样成立——**先有结构，后有载体**。
- 状态更新尽量由**刚跑完的那个子代理/主 agent 自己写**（子代理只能 `set` 自己那一个节点，main 可 `set` 任意节点；
  谁能新增节点见 §4.1）；若 main 写更省 token（结论已在 main 手里），就 main 写。

### 4.1 谁写什么（工具口径）

- **`init` / `add`（新增节点、连边）只由 main 做**：正在跑的节点不需要知道后面会新增什么，「图会长成什么样」
  只有 main 需要在意。工具**不硬拦**这层身份（只做数据校验），所以靠这条口径而不是靠报错。
- **子代理只 `set` 自己的节点**（`status` / `verdict` / `note` / `tokens`），也可 `get` 看摘要；
  **不得自行造节点**（`add` 会把图搅乱，也会被 main 的后续 `add` 撞上重复 id）。
- **子代理收尾自己 `set done` 时，宿主测的是它自己的会话**：读数落 `samples`，并把同一个 token 数写进
  节点 `tokens`（实测覆盖自报）；**main 给自己的调研节点收尾不填** tokens（那是整条主会话的累计，
  不是该节点的开销）。
- **会话归属解析到根会话**：工具沿子会话的 `parentSession` 上溯到 main，所以子代理写的**就是 main 会话的那张图**
  ——这也是「派活提示词里要写明子代理负责哪个节点 id」的原因。
- **派子代理前先把该节点的 `set` 成 `running`**：宿主 `subagent/start` 只回填「最近一个 `running` 且无 `agent`
  的节点」的 `agent` 字段；节点还是 `pending` 时这次回填会静默跳过（不会报错）。子代理崩了没收尾时，
  宿主 `subagent/end` 会把该节点收成 `done` + `verdict:"fail"` 并把 stopReason 写进 `note`。
- 面板 tab 在 DAG 出现后自动打开（判据见 §3.1：≥1 节点；挂载行 `openDagTab:false` 关闭）；面板 2s 轮询刷新，不需要手工刷新。

## 5. 分界节点

- **宿主 plan 正文定稿 = 分界**：此前 DAG 动态生长（本文件），此后为静态全景（`dag-exec.md`）。
- 分界只标注「到此调研结束」，不要求调研节点全部 `pass`：被否定的方向（`fail`）同样是有效结论，照常入图。

## 6. 纪律（与执行阶段共用）

- 不 `sleep`、不轮询 `list_agents`：派发后继续做独立工作，结算通知会自动到。
- 真被阻塞才 `job_output(<id>, wait: true)`，且只用于一次性后台 job，不用于子代理（见 `parallel-exec.md` §5）。
- 收串行/独占：git 与一切 mint 写、重命令（build / test:coverage / 装依赖）一律归 main。
